# 0002 — Розбирати виділений блок, а не всю відповідь

- **Status:** Accepted
- **Date:** 2026-08-24
- **Deciders:** Contributor, Tech Lead

## Context

Відповідь MCP-сервера — це текст. У нього можуть входити дані, а можуть — дані **разом із
прозою навколо**: пояснення, попередження, нагадування. Це не вада конкретного сервера, а
властивість формату: сервер має право говорити.

Стаття-джерело описує рівно цю пастку як реальну.

## Considered options

1. **Витягти виділений блок і розібрати його.**
2. **`json.loads` на всій відповіді** — працює, доки сервер мовчазний.
3. **Регулярка по всьому тексту** — знайти щось схоже на JSON де завгодно.

## Decision outcome

**Chosen:** Option 1.

Option 2 ламається на першому ж сервері, який ввічливий. Причому ламається в найгірший спосіб:
`JSONDecodeError` посеред виклику, за яким незрозуміло, чи сервер зламався, чи просто
привітався.

Option 3 гірша за обидві, і це варто назвати: регулярка знайде **щось** майже завжди. У прозі
трапляються фігурні дужки; у поясненні трапляється приклад. Парсер, який бере перше схоже,
одного дня візьме приклад із документації замість даних — і не скаже про це нічого.

Виділений блок дає однозначну межу: те, що між маркерами, — дані; те, що поза ними, —
не наша справа.

**Наслідок, який мусить бути окремим станом:** якщо блоку немає **зовсім**, це не порожній
результат. «Сервер нічого не повернув» і «сервер повернув порожній перелік» — різні події з
різними причинами, і зливати їх означає втратити половину діагностики (AC-03b).

## Consequences

**Positive**
- Проза навколо даних перестає бути проблемою.
- Відсутність даних називається, а не вгадується.
- Розбір перевіряється **без сервера**: підсунув рядок — подивився. Тому він в окремому модулі.

**Negative**
- Сервер, який не ставить маркерів, потребує окремої гілки. Названо в уроці як межа: справжні
  сервери різні, і перше, що варто зробити з новим, — подивитись на сиру відповідь.
