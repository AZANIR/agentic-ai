## The main thing

**The stage's central criterion had not been implemented.** AC-05 promised that the stage 3 graph
works through MCP with the same routes. `bridge.registry()` had **no consumer at all**, and my own
exercise 8 admitted as much in prose. A row of the test plan described a test that does not exist.

This is the heaviest finding of the course so far: not a mistake in the implementation, but **the
absence of an implementation underneath a green suite**.

## MINOR

exercise that does not exist; `scripts/spec_check.py` never returned a non-zero code, unlike its
two siblings; `chr(10).join` — the only occurrence in the repository; the NFR-5 numbers disagreed

block" had drifted from the SAD.

## The most important thing that happened AFTER the fixes

The mutation run showed that two of the just-fixed defects — somebody else's schema, and the
duplicate name — give **0 reds**. That is, I had fixed them, verified by hand in the console, and
**written no checks**.

The code was fixed exactly until the next refactor.

Hence the rule that went into PLAYBOOK: every review finding is closed by a **pair** — the code
fix, and a mutation in `mutations.json` that rolls that fix back. A mutation run after the fixes
shows not "did I fix it" but **"did I protect it"**.

One of the three checks added found something the manual verification had not thought of:
`required` must not name a field that is absent from the schema — otherwise the stage 1 validator
will demand something the model has no way to pass.

## What went from this into PLAYBOOK

Four lessons. The most useful is about exception groups: **one `BaseExceptionGroup` caused three
different defects in one module** — an empty cause, a message that looks like an explanation and
is not one, and the wrong phase. And the third one had to be fixed somewhere other than where it
appeared.

Second by weight is the "fix + mutation" pair. It did not come from theory: both just-fixed
defects were silently unprotected, and it was a run, not reasoning, that showed it.
